# Ordering, Manual Payment & WhatsApp Alerts

How a customer order travels through Mystery Bakebite after the move to **guest
checkout**. This supersedes the "account required before ordering" behaviour
described in `CUSTOMER_ACCOUNTS_AND_SECURITY.md`; that document now carries an
authoritative ORDERING RULE block that agrees with this one. Customer accounts are
not reachable from the site at all — the customer RPCs remain defined but no page
links to them.

---

## 1. What changed

| Before | Now |
|---|---|
| Customers had to register and verify an email before ordering | Guest checkout — no account, no session, no redirect |
| "Sign in" button in the header, "My Account" in the menu and footer | **Removed everywhere** — there is no customer sign-in entry point |
| `checkout.html` / `booking.html` bounced visitors to `account.html` | Both submit directly |
| `api_place_order` returned `auth_required` for anonymous callers | Accepts guests; links an account only when one is signed in |
| Administrators only could see orders | Guests see their own order through a private token link |
| No notification when an order arrived | WhatsApp alert to the baker, automatic |

**Customer accounts are no longer reachable from the site at all.** Every entry
point was removed: the header sign-in link (generated by `applyCustomerNav`, now
deleted), the "My Account" item in the slide-out menu and the footer, and the
account bar on the checkout page. `account.html` still exists on disk but nothing
links to it and no page references it; it can be deleted or re-enabled later
without touching the ordering flow.

**The Baker's Login is untouched.** The header sign-in button still maps to
`admin.html` (hidden for non-administrators), the mobile menu still carries it, and
`main.js` still appends a discreet **Baker Login** link to the footer legal line.

Administrator authentication and RBAC are **unchanged**. Guest checkout touched only
the customer-facing gate; every `api_admin_*` path still requires a Supabase Auth
session that maps to an active row in `public.admin_users`.

### What the customer does now

```
Browse  →  add to cart  →  Checkout  →  name + phone (+ optional email/notes)
        →  preferred date  →  collect or deliver  →  pay method  →  Submit
        →  confirmation: reference, summary, payment instructions, next steps
```

If they lose the confirmation, `order.html` has a **Find my order** form that needs
only the reference and the phone number used — no account.

### Mobile

The ordering pages use the existing single-column responsive layout: the field rows
collapse to one column, the date picker and quick-date pills stack, and the summary
panel moves below the form. The checkout now also has one less element (the account
bar), so the form is shorter on a phone.

## 2. The order lifecycle

```
Guest fills checkout
   name · phone · preferred date · delivery/collection
        │
        ▼
api_place_order  ── prices resolved from the catalogue, never the browser
        │           order ref  MB-XXXXXX  (or MC- for class bookings)
        │           32-hex security token
        ▼
orders row:  order_status   = 'submitted'   → shown as "Pending Review"
             payment_status = 'awaiting_payment' (or 'pay_on_collection')
        │
        ├──► WhatsApp alert to the baker
        │
        ▼
Confirmation page: reference, summary, payment instructions, next steps
        │
        ▼
Customer pays manually (MoMo / bank), uploads proof + reference
        │
        ▼
api_submit_proof → payment_status = 'payment_submitted'  → "Pending Verification"
                   (never 'payment_verified')
        │
        ▼
Administrator reviews evidence
        ├── approve → 'payment_verified' → the order may be confirmed/prepared
        └── reject  → 'payment_rejected' → customer may resubmit
```

### Status vocabulary

The database reuses the existing status columns; the labels the customer and baker
see map onto them:

| `order_status` | Displayed as | `payment_status` | Displayed as |
|---|---|---|---|
| `submitted` | **Pending Review** | `awaiting_payment` | Awaiting Payment |
| `confirmed` | Confirmed | `payment_submitted` | **Pending Verification** |
| `in_preparation` | In preparation | `payment_verified` | Payment confirmed |
| `ready` | Ready | `payment_rejected` | Payment not verified |
| `completed` | Completed | `pay_on_collection` | Pay in person |
| `cancelled` | Cancelled | `not_required` | No payment required |

No schema change was needed — `submitted` already meant "awaits baker review" and
`payment_submitted` already meant "awaits verification". Only the labels changed, in
`assets/js/order.js` and `assets/js/admin.js`.

## 3. Security model under guest checkout

Removing the login screen removes the session as an identity, so the **order token
becomes the capability**. This is the same model as a private tracking link.

**What the token unlocks** (and nothing more):
- `api_order(ref, token)` — read that one order
- `api_submit_proof(ref, token, …)` — submit payment evidence for that order

**What the token can never do:**
- Read any other order, list orders, or query by name/phone
- Change prices, totals, statuses, or the payment status
- Mark a payment verified — that requires `has_admin_permission('verify')`
- Reach any `api_admin_*` function

**Layered defences added for guests:**

1. **Unguessable tokens.** `gen_random_bytes(16)` → 32 hex characters, generated
   server-side. Never derived from the reference.
2. **Idempotency anti-replay.** `idempotency_key` is globally unique, so a guest who
   guessed another guest's key would otherwise receive that order's token. The RPC
   now only returns an existing order's token when the phone number matches, and
   returns `idempotency_conflict` otherwise.
3. **Per-phone throttle.** At most 5 guest orders per phone number per rolling hour
   (`rate_limited`), because the RPC is executable by `anon`.
4. **No account pivot.** If an order belongs to an account and a *different* account
   is signed in, the request is refused even when the caller holds the token.
5. **Unauthenticated writes still impossible.** `REVOKE ALL` on the order tables is
   unchanged; every mutation goes through a `SECURITY DEFINER` RPC.
6. **Pricing is still server-side.** A tampered `unitPrice`, `originalPrice` or
   `price` in the request body is ignored — the catalogue row wins.

### Residual risks (honest list)

- **Anyone holding the link can act on the order.** That is inherent to token-based
  guest checkout. If a link leaks, the holder can read the order and submit payment
  proof. They still cannot verify a payment or alter totals.
- **The guest throttle is per phone number.** Someone with many numbers can still
  place many orders. Supabase's anon rate limits are the outer bound.
- **Guest e-mail addresses are unverified** — they are recorded for contact only,
  never used to authorise anything.
- **Reference + phone lookup** remains a recovery path for a lost link; it requires
  the exact phone number, but it is a weaker secret than the token.

## 4. Manual payment & proof of payment

Payment instructions are read from `public.settings`, so the baker controls what
customers are told without touching code:

- `momo_name` / `momo_number` / `momo_provider` / `momo_note`
- `bank_name` / `bank_account_name` / `bank_account_number`
- `cash_pickup_enabled` / `cash_delivery_enabled`
- `advance_threshold` (default 70 000 pesewas = GH₵ 700.00)

A payment is shown as verified **only** after an authorised administrator confirms
it. Uploading a screenshot moves the order to *Pending Verification* and nothing
more.

Proof uploads are validated for extension/type and size, stored in the private
`proofs` Storage bucket (5 MB cap, `image/png`, `image/jpeg`, `image/webp`), and
readable only by verified administrators through the bucket's RLS policies.

### Orders submitted without proof

If a customer pays by cash, or simply does not upload anything yet, the order is
still recorded and clearly shows the outstanding action:

- cash orders → `pay_on_collection`, labelled "Pay in person"
- mobile money / bank with no proof → `awaiting_payment`, labelled "Awaiting
  Payment", with the payment instructions repeated on the confirmation page and on
  the order page

Nothing is ever auto-marked paid.

## 5. WhatsApp alert to the baker

### Message

Reproduced identically by `MB.orderAlertMessage()` in `assets/js/supabase.js` (used
for the fallback link) and by `buildMessage()` in the Edge Function:

```
🍰 *New Order Received | Mystery Bakebite*

A new order has been submitted on the website.

*Customer:* Ama Mensah
*Order Reference:* MB-261023-ABCD
*Order Summary:* 2 × Milky donuts, 6 pcs (Half dozen); 1 × Chocolate cake
*Requested Date:* Mon, 26 Oct 2026
*Payment Status:* Pending Verification

*Action Required:* Please log in to the admin dashboard, review the order and payment evidence, verify the payment, and approve or reject the order.

Please confirm payment before approving the order for preparation.
```

`Payment Status` reads **Pending Verification** when proof has already been attached
and **Awaiting Payment** when it has not.

### Delivery

`supabase/functions/notify-order/index.ts` — a Supabase Edge Function. The WhatsApp
API token lives in Edge Function secrets and is never sent to the browser.

**Deploy with JWT verification OFF.** The browser calls this function with the
publishable key, which is not a JWT, so the gateway would reject it otherwise.
The function performs its own authorisation instead:

```bash
supabase functions deploy notify-order --no-verify-jwt
```

Two triggers, both safe to enable together:

1. **From the browser.** `checkout.js` calls it immediately after the order is
   saved, passing `{ ref, token }`. The token proves ownership, so this cannot be
   used to spam other people's orders.
2. **From a Database Webhook** on `orders` `INSERT` (Dashboard → Database →
   Webhooks). Fully server-side; works even if the customer closes the tab.
   Send the header `x-notify-secret: <NOTIFY_WEBHOOK_SECRET>`.

Idempotent via `orders.notified_at` — a second call returns `alreadyNotified`
instead of sending twice.

**The webhook path fails closed.** Because the function runs with
`--no-verify-jwt`, an unauthenticated caller could otherwise force a notification
for any order reference they guessed. If `NOTIFY_WEBHOOK_SECRET` is not set, the
webhook branch returns 503 rather than trusting the request.

#### What the baker receives

```
🍰 *New Order | Mystery Bakebite*

*Reference:* MB-261025-ABCD
*Customer:* Ama Mensah
*Phone:* 0244123456
*Items:* 2 × Milky donuts, 6 pcs (Half dozen); 1 × Bread Making · Beginner
*Total:* GH₵2,550.00
*Date needed:* Fri, 30 Oct 2026
*Delivery to 12 Market Road, Tamale*
*Payment method:* Mobile Money
*Payment status:* Awaiting Payment

Log in to the admin dashboard to review, verify payment and approve.
```

The browser builds the same message, so the fallback link and the automatic send
cannot drift apart. `tests/security-tests.mjs` fails if the two field lists differ.

#### Automatic vs manual — read this carefully

| Path | Is a message actually sent? |
|---|---|
| Edge Function with `WHATSAPP_TOKEN` + `WHATSAPP_PHONE_NUMBER_ID` set | **Yes — automatic**, server to WhatsApp Cloud API |
| Edge Function deployed but credentials missing | **No.** Returns `sent:false`; the page offers the one-tap link |
| Edge Function not deployed (today's state) | **No.** One-tap pre-filled `wa.me` link only |
| One-tap `wa.me` link | **No.** It opens WhatsApp with the text pre-filled; **a human must press Send** |

Nothing in this project sends a WhatsApp message without the Cloud API
credentials. The UI says "Send the order alert" on the fallback button rather than
claiming it was already sent.

### If sending fails

The customer's order is already saved, so a failed notification never affects them
and never rolls back the order. `notified_at` stays `NULL`, so a later retry can
still deliver it. The confirmation page then shows a one-tap **"Send the order
alert to the baker on WhatsApp"** link, built from the business contact profile
(`settings.whatsapp_number`, falling back to the public `settings.whatsapp_contact`
line — the same resolution the Edge Function uses).

**WhatsApp 24-hour rule:** free-form text is only deliverable to a number that has
messaged the business within 24 hours. Outside that window you need an approved
template — set `WHATSAPP_TEMPLATE_NAME` and the function switches to template mode.

## 6. Configuration checklist

| Where | Setting |
|---|---|
| Admin → Settings | WhatsApp number (digits), MoMo + bank details, advance threshold |
| Edge Function secrets | `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, optional `BAKER_WHATSAPP_NUMBER`, `NOTIFY_WEBHOOK_SECRET` |
| GitHub repo secrets | `SUPABASE_URL`, `SUPABASE_ANON_KEY`, optional `BAKER_WHATSAPP` |
| Database → Webhooks | `orders` INSERT → `notify-order` (recommended; send `x-notify-secret`) |
| Storage | `proofs` bucket private |

## 7. Test evidence

`node tests/security-tests.mjs` — **129 passed, 0 failed**, including:

- Guest places a product order and a class booking with no account; both return a
  reference and a token; totals priced from the catalogue.
- Guest reads their own order with the token; refused without it and with a wrong one.
- Guest submits proof with the token; a second submission while pending is refused
  with `duplicate_submission`.
- Proof leaves the order at `payment_submitted`, never `payment_verified`.
- A different guest cannot read the order.
- The sixth guest order from one phone number in an hour is `rate_limited`.
- Another phone cannot replay a guest idempotency key (`idempotency_conflict`) and
  does not receive the original token.
- Checkout and booking no longer redirect to `account.html`, and checkout no longer
  refuses to submit without a session.
- The alert message contains the reference, summary, requested date, payment status
  and the review-and-approve instruction; the Edge Function keeps the WhatsApp token
  server-side.

`python3 tests/sql-parse-check.py` — **26 parsed, 0 failed** (both migrations, every
PL/pgSQL body).
